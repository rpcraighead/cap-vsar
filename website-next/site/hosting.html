HOSTING ARCHITECTURE

One machine runs the exercise. Everyone else brings a browser.

A V-SAREX does not need a rack of servers or a cloud account. One strong computer in the room runs the simulator, the observer's panel, the AI pilot and the exercise web pages; everyone else joins over Wi-Fi from a laptop, a tablet or a phone. This page shows how the pieces connect, what each seat needs, and what has and has not been measured on the machine we have.

THE LAYOUT

What runs where.

Everything an exercise needs sits on one wired workstation, called the sim box here. The simulator, the Mission Observer's panel software and the AI pilot are ordinary programs on the box. The exercise pages, the flight planner and the voice server run beside them as containers. A router or access point carries the Wi-Fi. A participant's device needs a browser and a headset; nothing of ours is installed on it.

CAN OUR WORKSTATION DO IT?

Can the workstation we have run all of it?

The short answer.

Probably, for one aircraft and a base of browser seats. It has not been shown. X-Plane with the AI pilot has been measured on this machine and has headroom, and the web services are tiny. Nobody has yet run everything at once with a room of devices and logged the result. Treat the rest of this section as the evidence, the gaps, and a rehearsal that closes them.

The workstation is, at the class level, a desktop with an 8-core, 8-thread Intel Core i7 of the ninth generation (boosting to about 4.7 GHz), about 30 GB of memory, a discrete NVIDIA GPU of the RTX 20 series with 8 GB of video memory, an NVMe drive and wired Ethernet. It has no Wi-Fi radio, so it needs a cable to the router. It runs Linux.

Recommendation, not a measurement.

For one aircraft and a base: a processor with 8 or more cores, 32 GB of memory or more, a discrete GPU with 8 GB of video memory or more, an SSD, a wired gigabit link to a dedicated access point (not a venue's shared Wi-Fi), and a battery backup. Start the box from a clean desktop with nothing else running. For two or more live aircraft, plan one simulator computer per aircraft and keep this one as the server and base.

Before the event, rehearse with everything running and the real devices joined, and fly a 20-minute sortie. The AI pilot's recorder already logs the simulator's frame time, so read it afterwards. A rule of thumb we would use: if the median stays at 30 frames a second or better and the slowest one percent stays above 20, there is headroom. If not, lower the simulator's graphics settings first, then move the web services to a small second computer, which is all they need. The project has run them on a separate lab server that way.

NOT ON THE SIM BOX

What does not run there.

  • Google sign-in. It needs the internet. With no internet, or with Google sign-in switched off, the sign-in page hides the Google button and takes badge codes, which need nothing outside the box.
  • Live weather and terrain lookups. The Flight Planner asks outside services for weather, winds aloft and terrain height. Without a connection it marks weather as simulated, plans in still air and shows terrain it could not read as unknown, not as sea level. Its FAA chart tiles come from a cache on the box.
  • Air traffic control. ATC is PilotEdge, an internet service the pilot's own X-Plane connects to. The mission net on the box is separate and carries exercise traffic only.
  • Source code, test runs and this website. They live elsewhere and play no part in an exercise.
  • A cloud copy. The project's notes describe a cloud deployment as a later option, and the planner's old cloud service is retired. A room on its own network needs neither.
  • Remote participants. Someone joining from home comes in through the squadron's private network link on the router, not through the sim box. This page describes the room.

IF THE WI-FI DROPS

What happens when the network goes.

  • On the box, nothing stops. The simulator, the AI pilot, the observer's panel on the box's own monitor and the DF plugin all work without the network. If the plugin cannot reach the console it keeps its last scenario and keeps computing, and it logs the trouble once. Position reports resume when the link returns.
  • Console pages in a browser (Mission Base, the Exercise Console, Debrief) show a reconnecting status and try again, waiting one second and doubling up to thirty. Mission Base then asks the console for the bearings and messages it missed.
  • The browser radio releases the push-to-talk and shuts the microphone the moment the link goes, then rejoins by itself on the same schedule. The Form 110 log is held in the browser tab and survives a reload. Export it before closing the tab.
  • Air Player and desktop Mumble clients depend on those programs' own behavior, which this project has not tested.

The reconnect behavior is fixed in the code and covered by automated tests. The acceptance test the project wrote down, dropping a tablet's Wi-Fi for thirty seconds and watching the radio rejoin, is not recorded as having been run on a real network.

Which doors are open, in outline.

The network doors a hosted exercise uses
DoorWho uses itNotes

A room on its own Wi-Fi needs nothing forwarded from the internet. On the box, allow the two inbound doors from the local network only. Do not assume the host's firewall also covers ports that Docker publishes; check from another device which doors really answer.
